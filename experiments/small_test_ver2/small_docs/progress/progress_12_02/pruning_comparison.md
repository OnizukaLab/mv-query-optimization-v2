# プルーニング有無による最適化結果の比較

## 概要

タイムステップ数8のシナリオにおいて、プルーニング（候補削減）を適用した場合と適用しない場合の最適化結果を比較しました。

**対象ファイル**:
- **Pruningなし**: `td_mv_optimization_result_8.json`
- **Pruningあり**: `td_mv_optimization_result_8p.json`

## 結果サマリー

| 指標 | Pruningなし | Pruningあり | 差分 (あり - なし) |
| :--- | :--- | :--- | :--- |
| **総実行時間 (Phase Time)** | **208.51秒** | 478.14秒 | +269.63秒 (遅い) |
| **ILP求解時間 (Solve Time)** | 1.09秒 | **0.13秒** | **-0.96秒 (高速)** |
| **プルーニング処理時間** | - | 467.79秒 | - |
| **ワークロードコスト** (Benefit) | -9,695,378 | -9,703,852 | -8,474 (良化?) |
| **マイグレーションコスト** | 2,135,090 | 2,240,896 | +105,806 (悪化) |
| **トータル目的関数値** (概算) | **-7,560,289** | -7,462,957 | +97,332 (悪化) |

※ 目的関数値は「ワークロードコスト + マイグレーションコスト」で、値が小さい（マイナスが大きい）ほど良いと仮定。

## 詳細分析

### 1. 実行時間のトレードオフ
- **ILPソルバーの高速化**: プルーニングにより候補数が削減されたため、Gurobiによる求解時間は **1.09秒から0.13秒へと約1/10に短縮** されました。これはプルーニングの意図通りの効果です。
- **プルーニングのオーバーヘッド**: しかし、プルーニング処理自体に **467.79秒** もかかっており、全体の実行時間は逆に **2倍以上** になってしまいました。
- **原因**: 現在のプルーニング実装（相関ルールの計算や頻出項セットの抽出など）が、削減できるILP求解時間に対して計算コストが高すぎる可能性があります。特にタイムステップ数やクエリ数が少ない場合、ILP自体が十分に高速であるため、プルーニングのメリットが出にくい状況です。

### 2. 解の質 (Quality of Solution)
- **目的関数値**: プルーニングなしの方がトータルで **約9.7万** 良いスコアを出しています。
- **意味**: プルーニングは探索空間を狭めるため、理論上、最適解は「Pruningなし」以下になります。今回の結果はその通りの挙動を示しており、Pruningによって「真の最適解」に含まれるべきいくつかのMV候補が誤って除外された（あるいは次点の組み合わせが選ばれた）可能性があります。
- **マイグレーション**: Pruningありの方がマイグレーションコストが高くなっています。これは、各タイムステップで最適なMVが見つからず、頻繁に入れ替えが発生したか、維持コストの高いMVが選ばれた可能性があります。

## 結論と今後の課題

現状の小規模な実験設定（タイムステップ8、クエリ数113）では、**プルーニングのオーバーヘッドがメリットを上回っており、逆効果** となっています。

**改善の方向性**:
1.  **プルーニング処理の高速化**: 相関ルール計算の効率化や、より軽量なヒューリスティックへの変更。
2.  **適用条件の見直し**: ILP求解に数分〜数時間かかるような「大規模・多タイムステップ」のシナリオでのみプルーニングを適用する。
3.  **パラメータ調整**: プルーニングの閾値（support, confidence）を調整し、計算時間を抑えつつ、必要な候補を残すバランスを探る。

## 追記: タイムステップ数12での比較結果

タイムステップ数を12に拡張し、周期的なワークロード（High/Lowの繰り返し）で同様の比較を行いました。

**対象ファイル**:
- **Pruningなし**: `td_mv_optimization_result_12.json`
- **Pruningあり**: `td_mv_optimization_result_12p.json`

### 結果サマリー (Timestep 12)

| 指標 | Pruningなし | Pruningあり | 差分 (あり - なし) |
| :--- | :--- | :--- | :--- |
| **総実行時間 (Phase Time)** | **469.77秒** | 800.45秒 | +330.68秒 (遅い) |
| **ILP求解時間 (Solve Time)** | 156.48秒 | **0.24秒** | **-156.24秒 (650倍高速)** |
| **プルーニング処理時間** | - | 785.08秒 | - |
| **ワークロードコスト** | -148,804,744 | -148,736,162 | +68,582 (悪化) |
| **マイグレーションコスト** | 2,366,890 | 2,350,996 | -15,894 (良化) |
| **トータル目的関数値** | **-146,437,854** | -146,385,166 | +52,688 (悪化) |

### 詳細分析 (Timestep 12)

1.  **ILP求解時間の劇的な短縮**:
    *   タイムステップ数が増えたことで、PruningなしのILP求解時間は **156.48秒** まで増加しました。
    *   一方、Pruningありの場合は **0.24秒** と、**約650倍** もの高速化を達成しています。
    *   これは、探索空間（候補MV数 × タイムステップ数）が広がるほど、プルーニングによる候補削減の効果が指数関数的に効いてくることを示唆しています。

2.  **プルーニングオーバーヘッドの課題**:
    *   しかし、プルーニング処理自体に **785秒** かかっており、トータルでは依然としてPruningなしの方が高速です。
    *   プルーニング処理の内訳を見ると、各ノードでのLocal ILP求解（60秒タイムアウト設定）や、候補の集約処理に時間がかかっていると考えられます。

3.  **解の質の維持**:
    *   トータル目的関数値の悪化は **約0.036%** (-52,688 / -146,437,854) に留まっており、**ほぼ最適解に近い解** を見つけられています。
    *   これは、プルーニングが「有望なMV」を正しく残せていることを示しています。

### 結論 (Timestep 12)

タイムステップ数が増えるにつれて、**ILPソルバーの負荷軽減効果は劇的に高まっています**。
現状のボトルネックは「プルーニング処理自体の重さ」にあります。もしプルーニング処理を高速化（例えば並列化や、Local ILPの簡略化）できれば、タイムステップ数がさらに増えた場合（例: 20, 50, 100...）に、トータル時間でも逆転する可能性が高いです。

## 追記: タイムステップ数16での比較結果

さらにタイムステップ数を16に拡張し、同様の比較を行いました。

**対象ファイル**:
- **Pruningなし**: `td_mv_optimization_result_16.json`
- **Pruningあり**: `td_mv_optimization_result_16p.json`

### 結果サマリー (Timestep 16)

| 指標 | Pruningなし | Pruningあり | 差分 (あり - なし) |
| :--- | :--- | :--- | :--- |
| **総実行時間 (Phase Time)** | **665.33秒** | 1,120.15秒 | +454.82秒 (遅い) |
| **ILP求解時間 (Solve Time)** | 246.67秒 | **0.47秒** | **-246.20秒 (524倍高速)** |
| **プルーニング処理時間** | - | 1,099.77秒 | - |
| **ワークロードコスト** | -198,405,936 | -198,345,493 | +60,443 (悪化) |
| **マイグレーションコスト** | 2,382,191 | 2,378,058 | -4,133 (良化) |
| **トータル目的関数値** | **-196,023,745** | -195,967,435 | +56,310 (悪化) |

### 詳細分析 (Timestep 16)

1.  **ILP求解時間の傾向**:
    *   タイムステップ数12の時と同様、PruningなしのILP求解時間は **246.67秒** とさらに増加しています。
    *   Pruningありは **0.47秒** と依然として一瞬で解けています。

2.  **プルーニングオーバーヘッド**:
    *   プルーニング処理時間は **1,099.77秒** となり、タイムステップ数の増加に伴いほぼ線形（あるいはそれ以上）に増加しています。
    *   現状のトレンドでは、ILP求解時間の増加ペースよりもプルーニング処理時間の増加ペースの方が早いため、トータル時間での逆転にはまだ至っていません。

3.  **解の質**:
    *   トータル目的関数値の悪化は **約0.029%** と非常に微小であり、Pruningによる解の劣化は無視できるレベルです。
