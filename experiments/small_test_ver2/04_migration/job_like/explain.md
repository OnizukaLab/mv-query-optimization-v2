### `non_leaf_3` のコストが高い理由の詳細分析

`non_leaf_3` の `[]` プラン（MV を使用しない場合）のコストが **29.48** と高くなっている理由を、クエリ構造とデータから分析します。

---

## 1. **`non_leaf_3` の構造**

[`qp_class.json`]qp_class.json ) から `non_leaf_3` の定義を確認：

```json
"non_leaf_3": {
  "node_id": "non_leaf_3",
  "operator": "Result",
  "children": ["non_leaf_1", "non_leaf_2"],
  "cost": 0.0,
  "rows": 1
}
```

- **子ノード**:
  - `non_leaf_1`: `leaf_1` を含む Limit ノード（コスト 0.0、実際は `leaf_1` = 13.14）
  - `non_leaf_2`: `leaf_2` を含む Limit ノード（コスト 0.0、実際は `leaf_2` = 12.98）
- **演算子**: `Result`（2つのサブクエリの結果を結合）

## 3. **コストが高くなる理由**

### **理由1: LIMIT の有無**
- **クエリ実行時（[`query1.json`]query1.json )）**: 
  - 各 Limit ノードは **1行のみ** を返すため、コストが 0.45 に削減されます。
  - Result ノード全体のコストは **0.91**。
  
- **MV 作成時（migration_costs.json の `[]` プラン）**: 
  - **LIMIT が無視され**、全データを処理する必要があります。
  - `leaf_1` のフルコスト: 13.14
  - `leaf_2` のフルコスト: 12.98
  - Result ノードのオーバーヘッド: ~3.36
  - **合計**: 13.14 + 12.98 + 3.36 ≈ **29.48**

---

### **理由2: 2つのサブクエリの独立実行**
- **`non_leaf_3` の構造**: 2つの独立したサブクエリ（InitPlan 1 と InitPlan 2）を実行し、結果を結合。
- **コスト計算**:
  - `leaf_1` のスキャンコスト: 13.14
  - `leaf_2` のスキャンコスト: 12.98
  - Result ノードのオーバーヘッド（メモリ操作、結果の結合など）: ~3.36
  - **合計**: 13.14 + 12.98 + 3.36 = **29.48**

---

### **理由3: Index Scan のコスト**
- **`leaf_1` (Index Scan on users)**:
  - インデックス `idx_users_city` を使用。
  - フィルタ条件: `(age >= 25)`
  - 推定行数: 42 行
  - コスト: 13.14（**インデックススキャン + フィルタ適用**）

- **`leaf_2` (Index Only Scan on users)**:
  - インデックス `idx_users_age` を使用。
  - 条件: `(age >= 25)`
  - 推定行数: 42 行
  - コスト: 12.98（**インデックスのみでデータを取得**）

- **両方とも高いのは**:
  - `users` テーブルが大きい（推定 50 行、実際はもっと多い可能性）。
  - `age >= 25` の条件で **42 行** をスキャン。
  - インデックススキャンでも、複数行を処理するため時間がかかる。

---

### **理由4: Result ノードのオーバーヘッド**
- **Result ノード**:
  - 2つのサブクエリの結果をメモリに保持し、結合。
  - CPU コスト: 各行のマテリアライズとメモリコピー。
  - **推定オーバーヘッド**: ~3.36（コスト全体の約 11%）

---

## 4. **なぜ migration_costs.json では 29.48 なのか**

[`migration_costs.json`]migration_costs.json ) の `non_leaf_3` の `[]` プラン = **29.48** は、以下の計算に基づきます：

```
leaf_1 のフルコスト (13.14) 
+ leaf_2 のフルコスト (12.98) 
+ Result ノードのオーバーヘッド (~3.36)
= 29.48
```

- **LIMIT がないため**、全データを処理する必要がある。
- **2つの独立したスキャン**が並行して実行され、コストが加算される。

## 5. **他のノードとの比較**

| ノード | `[]` プラン | 理由 |
|--------|------------|------|

## 6. **改善策**

### **1. MV の事前作成**
- `leaf_1` と `leaf_2` を MV として事前作成すれば、`non_leaf_3` のコストが大幅に削減されます。
- **例**: migration_costs.json の `['leaf_1', 'leaf_2']` プラン = **28.64**（わずかに低い）

### **2. インデックスの最適化**
- `users` テーブルに複合インデックスを作成:
  ```sql
  CREATE INDEX idx_users_age_city ON users(age, city);
  ```
- これにより、`leaf_1` と `leaf_2` のコストが削減されます。

### **3. ANALYZE の実行**
- PostgreSQL の統計情報を更新:
  ```sql
  ANALYZE users;
  ```
- これにより、コスト見積もりが正確になります。

---

## 7. **結論**

`non_leaf_3` のコストが **29.48** と高いのは、以下の理由によります：

1. **LIMIT の無視**: MV 作成時は全データを処理する必要がある。
2. **2つの独立したスキャン**: `leaf_1` (13.14) + `leaf_2` (12.98) = 26.12。
3. **Result ノードのオーバーヘッド**: メモリ操作とデータ結合で約 3.36 のコスト。
4. **インデックススキャンのコスト**: 各スキャンで 42 行を処理するため時間がかかる。

**改善策**: `leaf_1` と `leaf_2` を MV として事前作成し、`non_leaf_3` のコストを削減する。これにより、クエリ最適化の効果が最大化されます。
